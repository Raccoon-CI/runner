# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Raccoon CI is a self-hosted CI/CD platform. Users move their workflows from GitHub Actions, Travis, CircleCI or Azure Pipelines onto compute they choose.

- The MVP config format is GitHub Actions workflow YAML. Migrating from GitHub must be seamless and must not lose GHA features. A native config format may come later.
- Compute providers are pluggable. Priority: the user's own machines, then InstaBox (first sandbox target), then Boat.dev, then cheap clouds (DigitalOcean/Linode). AWS/GCP are out of scope. Runners are Linux only for now, and InstaBox machines run Debian 13 (trixie), not Ubuntu, even for jobs that say `ubuntu-latest`. Windows may come later on InstaBox; macOS is too costly to host, so it is only reachable through users' own machines. The parser still accepts `macos-*`/`windows-*` labels, because migrated workflows contain them.
- There are two ways to run a workflow. (1) The own engine (`raccoonci run`): Raccoon CI executes the workflow itself, so it must reimplement the runtime services official actions call (artifact, cache, OIDC, job summary); see `docs/gha-compat.md` for what act and Gitea already do. (2) The GitHub-triggered path (`raccoonci serve`, `internal/ghrunner`): GitHub still triggers and orchestrates the workflow, and a job whose `runs-on` has a `raccoon-*` label runs on an InstaBox machine through GitHub's own runner, which is the shape Blacksmith has. The project began as "own engine only, never a GitHub self-hosted runner orchestrator (the user rejects paying two bills)"; on 2026-10-31 the user, after studying Blacksmith, said that judgment may be wrong and asked for (2) to be built and measured. Which path is the product's main one is not decided: do not remove either, and do not call one of them "the" architecture.
- Planned: AI agents that triage or fix failed runs.

The code is a Go skeleton (module path `raccoonci`). The Makefile and layout follow the sibling project `../release-manager`.

## Commands

```sh
make build                # builds binaries into dist/ (VERSION=x.y.z sets main.version)
make test                 # go test ./...
make race                 # go test -race ./...
make vet                  # go vet ./...
make check                # vet + race — must pass before merging
go test ./internal/foo -run TestName -v   # run a single test
make runner-images        # refresh the embedded snapshot of GitHub's Ubuntu runner images (network)
```

## Layout

- `cmd/<binary>/main.go`: one directory per executable. Keep `main` thin: parse flags, wire dependencies, call into `internal/`.
- `internal/<pkg>/`: all application logic goes here (not importable from outside the module).
- `version` lives in `package main` and is set through `-ldflags "-X main.version=..."` in the Makefile.

New binaries also need to be added to the `build` target in the Makefile.

`raccoonci plan <workflow.yml>` parses a workflow and prints its jobs, matrix combinations, each run's `runs-on`, what each run needs installed, and warnings for OSes we can't provide. Use it to sanity-check the parser, evaluator and scanner against real workflow files.

`raccoonci run [-job id] [-secret NAME] [-var K=V] [-install none|toolchains|all] [-cache-protocol v1|v2] [-workdir dir] <workflow.yml>` runs a workflow on this machine. Actions are downloaded from GitHub, Node.js runtimes from nodejs.org, toolchains from nodejs.org and go.dev (all need network), and `actions/checkout` of the workflow's own repo copies the local working tree. Flags go before the workflow path. Before each job, what it needs is scanned and installed (`-install`): `toolchains` (the default) only writes into the user cache dir; `all` also installs apt packages with sudo, so it is meant for machines Raccoon CI owns, not a developer's laptop.

`raccoonci serve (-repo owner/name [-repo …] | -org name) [-label-prefix raccoon-] [-template ci] [-warm N] [-idle N] [-second-value 0.01] [-max-jobs 8] [-usage-file f]` runs the GitHub-triggered path: it polls the repositories for queued jobs whose `runs-on` label starts with the prefix and runs each on an InstaBox machine made from the `ci` template. The GitHub token comes from `GITHUB_TOKEN` (repo scope; with `-org` also `admin:org`), the InstaBox key from `INSTABOX_API_KEY`/`IBX_API_KEY`; neither is ever printed or put on a command line. See `internal/ghrunner` below and `docs/research/idle-runners/`.

`raccoonci-server -allow owner/name [-allow …] [-listen 127.0.0.1:18080] [-data-dir DIR]` (`cmd/raccoonci-server`) is the server being written (plan: `docs/server-design.md`; how to run it: `docs/server-dev.md`). Secrets come from the environment or `NAME_FILE` files of mode 600, never flags: `RACCOONCI_WEBHOOK_SECRET`, `RACCOONCI_API_TOKEN`, `RACCOONCI_GITHUB_APP_ID` + `RACCOONCI_GITHUB_APP_KEY_FILE` or `RACCOONCI_GITHUB_TOKEN`. `raccoonci-server replay payload.json` sends a signed recorded delivery. Jobs run only when told how: `-local-runner BINARY` (this machine, no isolation) or `-public-url` + `-snapshot` + the InstaBox key; otherwise runs stay queued. Docs are written in two versions, `x.md` (English) and `x.zh.md` (Chinese), kept in step.

Catalog flags go before the command: `-catalog extra.yaml` overlays a local file, `-catalog-url https://…` (env `RACCOONCI_CATALOG_URL`) pulls a feed, and `-catalog-key` (env `RACCOONCI_CATALOG_KEY`) requires its ed25519 signature. `raccoonci catalog update` refreshes the feed now.

## Architecture

Pipeline: `workflow.Parse` → `plan.Build` (evaluates what's knowable before the run, expands matrices, scans each instance's needs) → `engine.Run` (job graph; per instance it scans, `provision.Ensure`s, then calls) → `runner.Run` (one job instance). Runtime services: artifacts (v4) and cache (v1) are done. Also to come: the InstaBox provider. See `TODO.md` for the full picture.

**Knowledge that changes as tools evolve belongs in `internal/catalog/catalog.yaml`, not in Go code.** This covers:
- which commands belong to which toolchain, tool or apt package
- setup actions and their inputs
- version-file formats
- where the runner-images report states the defaults
- which Node.js major each `runs.using` runs on
- runner labels to OS (`ubuntu-*` → linux), which OSes are available, and the tracked runner images with their labels and toolset files
- the machine's own platform (Debian 13 / trixie) and the Ubuntu-to-Debian warnings (`lsb_release`, PPAs)
- how wrapper commands (`sudo`, `env`, `timeout`) and package installers (`apt-get install`) are read

Code holds only the mechanisms: parsers for the file formats it names, the report walker, the shell parser. When adding support for a tool, edit the YAML. A Go change is only needed for a new *kind* of rule.

What stays in code on purpose is GitHub's own protocol, which changes with GitHub's releases, not with the tool ecosystem: workflow and `action.yml` keys, workflow command names, expression syntax, shell command lines, and limits such as 256 matrix jobs. Download locations (GitHub, nodejs.org) also stay in code, because the catalog may come from the network and must not be able to redirect downloads.

The catalog is layered: built-in, then a feed pulled from `-catalog-url` (cached on disk, refreshed daily with ETag, optional ed25519 signature), then the local file. Because it may come from the network, a catalog only *names* things: every name is checked against a strict character set, and it cannot hold commands or URLs. A failed pull never stops a run: it falls back to the cache and then to the built-in one, and says why on stderr.

- `internal/value`: the dynamic data model shared by the parser and the expression evaluator. Values are nil/bool/float64/string/[]any/`value.Object`. `Object` is an *ordered* key list, because matrix expansion order and GitHub's generated job names depend on key order. All numbers are float64, matching GitHub (so `3.10` becomes `3.1`, as it does there). `value.Decoder` walks `yaml.Node` trees with a shared node budget, which guards against alias bombs in untrusted PR workflow files. Use one Decoder per document.
- `internal/workflow`: `Parse` turns workflow YAML into `Workflow`/`Job`/`Step`. Fields that may be literals or `${{ }}` expressions stay as raw `any` values and are evaluated later. Like GitHub, it rejects unknown keys, missing `runs-on`/`steps`, bad needs and cycles. `ExpandMatrix` implements GitHub's include/exclude rules and takes an already-evaluated matrix; dynamic matrices (`${{ fromJSON(...) }}`) must go through the evaluator first. The matrix tests encode the examples from GitHub's docs, so keep them passing.
- `internal/expr`: a hand-written lexer, parser and evaluator for `${{ }}`, following GitHub's documented semantics: mismatched types compare as numbers, strings compare case-insensitively, `&&`/`||` return operands, `*` object filters, and objects/arrays are equal only to the same instance. `Interpolate` keeps the type of a lone `${{ x }}` (so `false` stays falsy and `fromJSON` can build a matrix) and stringifies mixed text. `EvalCondition` adds the implicit `success() &&` and treats mixed text as an always-true string, as GitHub does. A missing context returns `*expr.UnknownContextError`, which `plan` uses to defer values that are only known at run time.
- `internal/plan`: expands each job into `Instance`s (one per matrix combination), evaluating `runs-on` with `matrix`/`strategy` contexts. `Instance.Unavailable()` flags OSes the catalog says aren't available (`UnavailableMsg` carries the text). `internal/platform` just reads `runs-on` values and asks the catalog. Product rule: those runs fail with a clear message or go to a user-connected machine. They are never skipped silently and never moved to Linux.
- `internal/runnerimages`: what GitHub's hosted Ubuntu images preinstall (default tool versions, toolcache versions, apt packages, CLIs), so jobs that rely on preinstalled tools get the same versions here. `Fetcher.Latest` reads the *fully deployed* release from runner-images' README status badge (a gist, not the API: no token, no 60/hour limit). It falls back to the releases API (newest non-prerelease) when the badge is missing, malformed, or names a version whose report can't be downloaded. Data per release comes from the `internal.<image>.json` release asset, plus the toolset at the same tag for Go's default. Which images exist, their labels and toolset file names come from the catalog, and `ubuntu-latest` is resolved from the README table (`Snapshot.Aliases`, written to `aliases.json`). `Snapshot.ForLabel(cat, label)` needs the catalog. The embedded `snapshot/` is the offline fallback. The planned server will poll the same sources into its database. Only send the token to api.github.com.
- `internal/catalog`: loads and validates `catalog.yaml`. The file is embedded, and `Overlay` applies another catalog on top: same-name entries replace, `name: null` removes, top-level lists replace. Validation rejects:
  - unknown keys
  - a command claimed by two entries
  - references to undefined toolchains
  - unknown version-file formats
  - names with characters that could inject options or paths (`-o…`, `../`)
  - bad regexps and unknown message placeholders

  A catalog with a higher `schema` than the code understands is refused as a whole (`ErrNewerSchema`). `TestDefaultIsValid` guards the embedded file. `Source` (`source.go`) pulls a feed:
  - https only, no redirect downgrade
  - size-capped
  - conditional requests with ETag
  - the cache is rewritten only after the new file has been verified and validated
  - cached content is re-verified on every read, so a tampered cache file is ignored
- `internal/scan`: a static, best-effort scan of what a job instance needs installed. It never fails a job.
  - Explicit demands are `setup-*` versions, from inputs, matrix values, or version files like `.nvmrc`/`go.mod`/`.tool-versions`.
  - Implicit demands are commands found in `run:` scripts that the GitHub image preinstalls and that no earlier step set up. Scripts are parsed with `mvdan.cc/sh`, not regex. Implicit demands use the image's default versions from `runnerimages`, and are only reported when that image really has the tool.
  - What commands, actions and files mean comes from the catalog.
  - Opaque build commands (`make`, `./x.sh`) plus a repo manifest (`go.mod`, `package.json`, ...) imply that toolchain.
  - It warns about the catalog's `compat-warnings` (Ubuntu-only patterns such as `lsb_release` and PPAs) and YAML-float versions (`3.10` → `3.1`, with the affected versions listed per toolchain in the catalog).
  - Container jobs only need docker.
  - It looks inside actions the catalog has no rule for (`inside`): a docker action needs docker; a composite action's steps are scanned like any others (depth 4, a repeat on the stack stops), with `inputs` taken from the calling step's `with` or the action's defaults (an input that can't be evaluated yet is left out, so it reads as null) and `runner.os` = Linux, and a step whose `if:` is false there is skipped while one that can't be decided stays. Remote actions come from `Input.Action` (the engine passes `actions.Store.Lookup`, sharing the runner's download; `raccoonci plan -fetch-actions` does the same offline-by-default plan), local ones (`./path`) from the repo FS. Not done: the workflow's own steps' `if:`.
  - Repo reads are size-capped. Pass an `os.OpenRoot` FS (as `raccoonci plan` does) so symlinks can't escape the repo.
- `internal/provision`: installs a job instance's scanned demands before it runs, and never fails the job (everything that goes wrong comes back as a `Failed` item, which the engine shows as a warning, because the scan is only a heuristic).
  - Toolchains go into the tool cache in toolkit's layout (`<tool>/<version>/<arch>` plus an `<arch>.complete` marker), so `setup-*` actions find them and download nothing. Like those actions, a cached version that satisfies the spec wins over asking the network, so offline works.
  - Before downloading, a copy already installed on the machine is used if it satisfies the spec: a provider's template may ship Go, Node.js... (InstaBox's `universal` does). The catalog's `toolchains.<name>.probe` says what to run and which capture group of the output is the version; the install root (`<root>/bin/<command>`, symlinks resolved) is then symlinked into the tool cache as `<tool>/<version>/<arch>` with the `.complete` marker, so `setup-*` finds it. Probed at run time, never hardcoded, because template versions change. A toolchain without a probe (Python: the system one is not what `setup-python` expects) is always downloaded. `complete()` also stats the install directory, so an adopted link whose original is gone does not count as cached.
  - Downloads are unpacked into a private dir, verified (SHA-256), then renamed into place. Concurrent jobs share one download.
  - A toolchain the job uses *without* setting it up (an implicit demand) is also returned in `Result.PathDirs`, which the engine passes to `runner.Config.PrependPath`.
  - The catalog picks an `Installer` by name (`installer: node`); the installers themselves (nodejs.org, go.dev, python-build-standalone, static.rust-lang.org, api.adoptium.net) are code. `implicit-only: true` (java, rust) means the setup action (`setup-java`, rustup) installs by itself, so the tool cache is only filled for a job that uses the tool without setting it up. Rust is installed component by component (rustc, cargo, rust-std, rustfmt, clippy), each checked against the SHA-256 published next to it and installed with its own `install.sh`; it takes `stable` or an exact version. Java is Temurin from Adoptium, by major or exact version (`1.8` is 8; a `+build` suffix is dropped; the newest build of a version is used). Neither probes for a copy already on the machine.
  - **Python comes from python-build-standalone, not GitHub's builds.** GitHub's Python builds are for Ubuntu, and `setup-python` refuses to install them on Debian ("version … was not found for this operating system"; verified on a clean Debian 13). Prefilling the tool cache (`Python/<ver>/x64`) works because `setup-python` finds it there and never consults its manifest. That release only keeps the newest patch of each minor, so an *implicit* demand (the job just calls `python3`; the image has 3.12.3) is relaxed to the newest patch of the same minor, while a version the workflow *names* is never swapped (`Demand.Declared` marks an implicit demand that is also named later).
  - Tools without an installer are only checked for. apt packages are installed through `Apt` (root or `sudo -n`; Debian names from the catalog's `debian:` field; one bad package doesn't block the rest), and only when the caller sets `Provisioner.Apt`.
  - The tool cache is bounded by `provision.Prune` (`raccoonci run -toolcache-limit-gb`, default 10, 0 = none), called once at the start of a local run, not on the machines of `-on instabox`. A version's last use is the mtime of its `<arch>.complete` marker, which `Provisioner.touch` refreshes whenever the version is chosen; the least recently used go first, nothing used within 24 hours is removed (so the limit is soft; it must exceed a job's run time), and hidden leftovers of interrupted installs older than that are swept. Links to a machine's own copy count as nothing. Versions that `setup-*` actions wrote themselves are pruned too (they download again).
- `internal/blob`: where artifact bytes live. `Store` is a small interface (multipart `BeginUpload`, `PresignGet`, `Stat`, `Delete`) shaped for the planned artifact service: a block is forwarded as one part without landing on disk, and downloads are presigned URLs that bypass our server. `Dir` implements it on a local directory (downloads go through `Dir.Handler`, with HMAC-signed links), for single-machine runs. `S3` implements it with the official `aws-sdk-go-v2` for any S3-compatible store (`Endpoint` + `PathStyle` for MinIO, R2 and the like). Checksums are set to "when required" because many compatible stores reject the SDK's default CRC trailers, and parts are sent with an unsigned payload because their hash isn't known up front. Unit tests run against an in-process fake S3. `TestRealS3` (skipped unless `RACCOONCI_TEST_S3_ENDPOINT`, `_KEY`, `_SECRET` are set) was run against SeaweedFS's S3 gateway, including a wrong-secret check; MinIO no longer publishes binaries or images. AWS itself has not been tried.
- `internal/artifact`: the artifact protocol of `upload-artifact`/`download-artifact` v4+, so they run unchanged. Two halves, as on GitHub. Metadata is the Twirp `ArtifactService` (Create, Finalize, List, GetSignedArtifactURL, Delete, JSON only) at `ACTIONS_RESULTS_URL`, authenticated by `ACTIONS_RUNTIME_TOKEN`, an HS256 JWT whose `scp` claim `Actions.Results:<run>:<job>` is what the toolkit reads. A token opens only its own run, and only its own job may create. Data is a small imitation of Azure Blob: `CreateArtifact` returns a signed URL on our server, and an `azblob.Upload` behind it receives the SDK's calls (see `internal/azblob`). Downloads need no imitation: the store's presigned URL is returned. FinalizeArtifact checks the stored size against the client's; the client's sha256 is recorded and returned as `digest`, not verified. Metadata is in memory, and in an optional `Index` (`Config.Index`: `Load` at start, `Save` when an artifact is finalized, `Delete`) that the server backs with its database; without one a restart forgets it, as `raccoonci run` does. `Config.Keep`/`MaxKeep` set the default time to keep and cap what a client asks for; `Service.Expire`, `Artifacts` and `DownloadURL` serve the server's sweep and API. `raccoonci run` starts the service on a loopback port with a `blob.Dir` under the workdir, and also on a job network's gateway for container jobs (see `internal/runner`). Verified end to end with the real `upload-artifact@v4` and `download-artifact@v4` (20 MB, three blocks, two jobs). Not done: artifact v3 (REST), per-job tokens (a local run uses one token for all jobs), retention enforcement in `raccoonci run` (the server sweeps).
- `internal/azblob`: receives one blob from a client that thinks it is talking to Azure Blob Storage, and writes it into a `blob.Store`. One `Upload` sits behind one signed URL and implements the calls `@azure/storage-blob` makes: Put Block and Put Block List (files the SDK sends in blocks), and Put Blob (files small enough for one request; `@actions/cache` v2 sends up to 128 MiB that way). If the first block id has the SDK's shape (`base64(36-char prefix + 12 digits)`), block i is forwarded as part i+1 of a multipart upload without touching disk, and the block list must be exactly 0..n-1 in order (unlisted blocks are dropped, as Azure does). Any other id shape takes a spool path: blocks wait on disk and are cut into `partSize` parts at commit. The first request fixes the mode, and a blob written with Put Blob refuses blocks (409). An empty blob is refused. A repeated Put Blob that already succeeded is a no-op, since clients retry after a lost reply.
- `internal/twirp`: the shared parts of the Twirp JSON protocol (errors with their HTTP status, replies, and a request reader that accepts snake_case or camelCase names and 64-bit integers as strings). Used by the artifact and cache services.
- `internal/cache`: the cache protocols of `actions/cache` and the `cache:` option of `setup-*`. v1 is REST under `/_apis/artifactcache/` at `ACTIONS_CACHE_URL` (`GET cache`, `POST caches`, `PATCH caches/{id}`, `POST caches/{id}`), same runtime token as artifacts. v2 is the Twirp `CacheService` (CreateCacheEntry, FinalizeCacheEntryUpload, GetCacheEntryDownloadURL) at `ACTIONS_RESULTS_URL`: CreateCacheEntry hands out a signed upload URL, an `azblob.Upload` receives the data, and Finalize turns the upload into an entry. Refusals (the entry exists, another job is saving it, wrong size) are ordinary replies with `ok: false` and a `message`, because the client reads those; only malformed requests and server faults are Twirp errors. Both protocols are always served and share one set of entries, because the client computes `version` the same way in both. Which one the client uses is decided by `ACTIONS_CACHE_SERVICE_V2`: `Env` sets it to `true` when `Config.AdvertiseV2` is on (`raccoonci run -cache-protocol v2`) and clears it otherwise, so a value inherited from the host cannot switch the client. The toolkit uses v1 unless that variable is set. Upload URLs of v2 are signed in their own realm (`~cache`), which no run id can equal, so an artifact upload URL cannot write into the cache. The `CacheMetadata` of v2 requests (repository id and scopes) is ignored. Matching follows the docs: per key in order, an exact match wins, else the newest entry whose key starts with it, within the same `version`. Entries are immutable once committed (409 on a second reservation; an unfinished reservation older than an hour is replaced). Chunks are placed by `Content-Range`, wait on disk (in a private directory made by `azblob.NewSpoolDir` under `Config.SpoolDir`, which `raccoonci run` puts next to the store, never in a small `/tmp`; the artifact service does the same), and are cut into `partSize` parts at commit, because the client picks the chunk size (`upload-chunk-size`) and the store needs 5 MiB parts. Committed entries are listed in `index.json`, so a cache outlives the process; `raccoonci run` keeps it under `<user cache>/raccoonci/actions-cache/<hash>-<repository>/`. An entry whose object has vanished from the store is dropped at lookup. Verified end to end with the real `actions/cache@v4` and `actions/cache/restore@v4`, two jobs each: v1 with 20 MB in 1 MiB chunks and a second process that hit the first one's entry; v2 with 20 MB (one Put Blob, also hit by a second process) and 150 MB (above the SDK's 128 MiB single-shot limit, so sent in blocks). `Config.MaxBytes` caps the committed entries (`raccoonci run -cache-limit-gb`, default 10 like GitHub, 0 = none): when a new entry would exceed it the least recently used go first (`record.Used`, updated on a lookup hit and saved with the index at the next commit), and an entry larger than the cap is refused (400 at reserve or commit, `ok: false` in v2). `Config.Free` (a `statfs` of the store's disk in `raccoonci run`) is checked before an entry is assembled: older entries are evicted until it fits with 256 MiB to spare, otherwise the commit fails with 507. With v2 the data is stored before Finalize, so eviction happens after it. `raccoonci run -cache-s3-bucket …` (`cmd/raccoonci/cachestore.go`) keeps the entries in an S3-compatible bucket instead of on the controller's disk: `startCache` then gets a `blob.S3` store with the prefix `<-cache-s3-prefix><repository dir>/`, no `Free` check, and clients download from presigned bucket links; credentials come from `RACCOONCI_CACHE_S3_KEY`/`_SECRET`/`_TOKEN`. `blob.S3.PutPart` reads a non-seekable part up to 32 MiB into memory so the SDK can retry it. Verified against SeaweedFS's S3 gateway, not a real external bucket. Not done: scoping by branch (every ref of a repository shares one cache), concurrent `raccoonci` processes writing one index (last writer wins), and a separate secret for the cache's download links (it shares the run's key).
- `internal/envsnap`: when a snapshot of a prepared environment (dependencies installed) can be reused. `Compute` hashes the lockfiles (`toolchains.<name>.lockfiles` in the catalog) of the toolchains a job uses, plus the machine image's identity, into a key. Every project of a used toolchain counts, in the root or below it (a project is a directory with a manifest or lockfile of that toolchain; `.git`, `node_modules`, `vendor` and the like are skipped, the walk is capped): each lockfile goes in under its path from the root, so a change in `backend/go.sum` gives a new key. A manifest with no lockfile in the same directory makes the project unsnapshottable (`ErrUnpinned`: nothing says when its dependencies change), even when a lockfile sits in an ancestor directory (nothing says the manifest is a workspace member). The key covers all projects of the toolchain, not only those the job works in, which can rebuild a snapshot more often than needed but never reuses a stale one. A toolchain with no lockfile anywhere and no manifest needs nothing. Toolchain *versions* are deliberately not in the key: toolchains come with the machine or are installed on demand, the snapshot is for what they install. `Index` is the file that maps keys to the provider's snapshot ids, holds at most N and returns the least recently used (and replaced) ones for the caller to delete. `raccoonci plan` prints per instance whether it could be snapshotted. `raccoonci run -on instabox -env-snapshots N` wires it in (`cmd/raccoonci/remote.go`, `instabox.RunOptions`/`Client.Snapshot`): a hit starts the machine from the snapshot (if it is gone, 400/404, the entry is dropped and the instance reruns from the runner snapshot); a miss lets the first successful run per key clean its machine, snapshot it in the background and then delete it, and evicted entries are deleted through the API. Verified on InstaBox with a small Go project: miss and save, hit (build 4.2 s to 0.3 s), changed go.sum saves a new snapshot and evicts the old one. Rules, in the package comment: snapshot only from trusted refs (never a fork PR, whose install scripts could poison every later run with the same lockfile) and only from a machine with no secrets on its disks, since a snapshot copies sign-ins too. Measured on InstaBox (cli/cli): restore 6 to 12 s plus a 2.9 s warm build, against ~39 s cold; see the memory notes before assuming it pays for small projects.
- `internal/sched`: decides which job instances share a machine. `History` keeps the last 5 on-machine durations per workflow file and instance name (a JSON file under `<user cache>/raccoonci/sched/`, replaced atomically; a damaged file reads as empty). `Policy.Short` says an instance is short when its median is under 3 times the median start-up measured in this run (10 s before any machine has come up). No history means long: packing a long job costs it CPU, a lone short job costs one start-up, and the history corrects the next run. `instabox.Pool` runs the short ones: it fills a machine up to its slots (default one per vCPU, learned from the first machine; `-pack-slots`) before creating another, keeps an empty machine 15 s, and deletes all at `Close`. Each slot has its own agent config file (`dispatch.SlotConfig`), written by the pool and deleted by the agent when read, so the runner snapshot's agent runs `agent -loop -slots 8`. Instances with `container:`/`services:` or that can start from an environment snapshot are not packed. `-no-pack` turns it off. Not done: fixed-port clashes between packed jobs, a warm machine pool, real-benchmark numbers (see `TODO.md` C.3).
- `internal/dispatch`: sends a job to a machine over a connection the machine opens (`raccoonci agent`). `Controller.Submit(Job)` returns a `Run` with a random token; the agent presents it as a bearer token on `GET /v1/job`, `GET /v1/source` (the source tree as .tar.gz, `TarDir`), `POST /v1/log` (chunks at `X-Offset`: a resent chunk only writes its new tail, a gap is a 409 with `X-Expected-Offset`), `POST /v1/heartbeat`, `POST /v1/done`. The controller keeps only the token's SHA-256, so a token opens its own job only, and there is no unauthenticated route (the address may be public). `Run.Wait` fails when the machine never calls (`StartTimeout`, 2 min) or goes silent (`Lease`, 30 s). The agent runs `raccoonci run [-secret NAME…] <Job.Args>` as a subprocess in the unpacked source, with `Job.Env` and `Job.Secrets` in its environment, and ships stdout and stderr; it refuses a controller URL that is not https (or http on a loopback address), because the token and secrets travel on it. Config is read from a file (`/etc/raccoonci-agent.json`, polled until it appears), never the command line. The reason for this shape: InstaBox allows 32 concurrent exec requests across the account, and a machine has no inbound address. - `internal/trigger`: whether an event starts a workflow, from `Workflow.On`. `Match(on, Event)` handles the three spellings of `on:`, `types` (pull requests default to opened/synchronize/reopened), and for push and pull requests GitHub's filters: `branches`/`tags` and their `-ignore` forms (a push of a tag with only `branches` listed does not trigger, and the reverse; a pull request's branches apply to its base; both a filter and its `-ignore` is an error), and `paths`/`paths-ignore` (tag pushes skip them; `Event.Files == nil` means unknown, so the filter does not block). - `internal/ghrunner`: the GitHub-triggered path, `raccoonci serve`. GitHub keeps triggering and orchestrating (so every workflow feature works as there); we only supply runners.
  - **Flow.** `Client` (GitHub REST; every GET sends the ETag back, a 304 costs no rate limit, which is what lets it poll every second) lists queued and in-progress runs per repository (`ActiveRuns`, `RunJobs`); a queued job with a label starting with `-label-prefix` (default `raccoon-`) gets a just-in-time runner (`generate-jitconfig`, runner group 1) and a machine from the InstaBox `ci` template (Ubuntu 24.04, GitHub's own runner image with the runner 2.338.2 at `/opt/actions-runner`, unconfigured). Both are created in parallel; the JIT config is written to the machine with `PUT /files` (mode 0600) and read by `run.sh --jitconfig "$(cat file)"`, so it is never on a command line or in a log (a test asserts it). `follow` polls the runner each second until GitHub removes it (a JIT runner is single-use), then the machine is deleted. A job that finds no runner within `IdleTimeout` (3 min) is given up on, up to 3 attempts. A runner started for a job whose job another (waiting) runner took is released after about 10 s (`takenCheckAfter`), not after the timeout.
  - **Idle runners** (`keepalive.go`, `docs/research/idle-runners/` has the model, a simulator and the numbers measured on real traces). A waiting runner is a running machine (about $1 a day for 4 vCPU / 8 GiB), but a job that finds one starts in about 1 s instead of 10 s. `KeepAlive` decides how many to keep after jobs have come: the cost of a waiting second is `C`, the worth of a second of a job waiting is `V` (`-second-value`, default $0.01, 0 turns the policy off), a refill takes `R` = 8 s, and a hit saves `Δ` = 8 s. Per gap between bursts of arrivals (bursts within 30 s are one) it keeps a runner for the TTL that minimises cost + V×latency over the last 100 gaps; before 20 gaps it uses the ski-rental break-even `V·Δ/C`. The pool size follows the burst size (EWMA, at most 4). `Service.Idle` is a floor. Surplus waiting runners are retired (their registration is deleted first, which GitHub refuses for a runner that has a job, so retiring is safe).
  - **Known arrivals** (`prestart.go`, `cron.go`) need no policy: a workflow's `schedule:` cron is read from the repository's workflows (re-read every 10 min; `ParseCron` is UTC with lists, ranges, steps, dom/dow OR) and a runner is started `R` seconds before each fire time and kept until +10 min (GitHub starts scheduled runs minutes late). A job that `needs` a job in progress gets a runner just before the running one is expected to finish, from the median of its last durations (`sched.History` under `<user cache>/raccoonci/serve/durations.json`, keyed by repository and job name; recorded from completed jobs); no known duration means no guess. Both are `expectation`s.
  - **Step progress** (`progress.go`): the jobs API lists a job's steps with their status, so the time a running upstream job has left is what its unfinished steps take (each step's median, remembered per repository, job name, step number and name when a job completes; the step it is in counts for its median less what it has run, and a step that has overrun its median counts as done at once, so the estimate leans early) instead of the whole job's median; a step with no history falls back to the job median. A run with a job waiting for one still running is `track`ed and looked at every second (`refreshTracked`, ETag requests) even when webhooks make the normal listing come every 30 s, and an expectation seen again has its moment updated. When a job a runner was started ahead for is first seen, `reportPrediction` logs how far each estimate (steps, and the job median alone) was from the time GitHub queued it. Measured live (2026-11-01, a `build` with one random 5–24 s step and a `deploy` that needs it, 8 predictions, a deliberately noisy case): mean absolute error 5.3 s by steps and 5.0 s by the job median, but by steps the runner was never late (errors −9 to −2 s) while by the median 4 of 8 were late (up to +9 s, which with about 7 s to start a runner means a cold start); the downstream job started 1 s after being queued in every run with history. Early costs about 10 s of a machine, late costs a cold start of 6 s, so not being late matters more.
  - **Matrix jobs** (`matrix.go`): a job with a matrix is queued as one job per combination, all at once, so `instancesOf` says how many runners to start ahead: a matrix written out in the workflow is counted with `workflow.ExpandMatrix`; one with a `${{ }}` in it (`fromJSON(needs.plan.outputs.x)`) is not known until the job that builds it finishes, and GitHub's API does not return job outputs (to my knowledge), so the **largest** of the last five counts seen on earlier runs (`recordCount`, kept in `sched.History` as that many seconds, once per run and job) stands in for it. Largest, not median, because a runner too many waits about 15 s (a fraction of a cent) and one too few leaves a job a cold start of about 7 s: on eight live runs of a matrix of 2 to 5 jobs (counts 2 4 3 2 2 5 5 4) the median left 8 of 25 jobs to a cold start and wasted 2 runners (live), and the maximum, run live at one run every 100 s (7 runs with history, counts 4 2 5 5 4 4 4), left 1 of 28 jobs to a cold start and wasted 5 runners. **It only holds while the start limit is not tight**: at one run every 62 s (5 to 6 starts per run against 10 a minute) the limit kept back part of the runners started ahead and the maximum did no better than the median (about 30% of jobs cold in both); the log line `N of those M runner(s) not started: the start limit …` says when that happens (before it was silent). Capped by `max-parallel` and by `MaxJobs`; no history means one. An expectation carries the count and starts that many together.
  - **Start limit** (`starts.go`): InstaBox lets an organization start a limited number of machines a minute (10 on the Pro plan; the API refuses with 429 beyond it). `serve -starts-per-minute` (default 10, 0 = no limit) makes the service count its own starts in a sliding 62 s window and keep the last three for jobs that are queued: a runner started ahead of a job that is not queued yet (`speculative`) may not use them. A start refused by our count or by a 429 does not use up an attempt of the job: it is asked again after a wait (`serving.notBefore`, `startHold` 20 s after a 429, which also holds all starts). Before this, three quick 429s gave a job up for good and it stayed queued for ever. Warm runners do not use starts, which is part of what keeping them is worth when a matrix fans out.
  - **Runners are interchangeable.** GitHub gives a runner the oldest queued job that its labels fit, not the job it was started for, so with a backlog or a fan-out a job can be left queued after the runner started for it has run another one. `startFor` looks at the job when its runner has gone and, if it is still queued, asks for another runner (the attempt is not used up if the runner did work). Also, only runners kept waiting count as free (`idleCountLocked`, `launching`): one started for a job is spoken for, and counting it had given the fourth job of a fan-out a promise to the runner of the third and made it wait the 20 s the promise lasts. Each of these three was found by a live run and has a test that fails without the fix.
  - **Pools.** Without `-org` each repository has its own pool and its runners are registered with the repository. With `-org` (one loop for all the repositories watched, all of the organization's when no `-repo` is given) the runners are registered with the organization (runner group 1, `Default`; its visibility must include the repositories, and a public repository needs the group to allow public ones), so a waiting runner takes a job of any repository: the biggest saving in the research, since one repository's burst keeps a runner for the others. `poolOf(repo)` is the one place that maps a repository to its pool; `liveRunner.repo` is the pool's scope (`org:<name>` or the repository), `liveRunner.jobRepo` where the job is. A runner of the organization can take any job with the labels, from any repository of the group, so repositories that do not trust each other must not share a pool.
  - **Machine size** (`size.go`): a job's `runs-on` label `raccoon-<N>vcpu` asks for N vCPUs; the memory is the one InstaBox gives that many (the sizes the organization may create are read once from `GET /v1/orgs` `allowedSpecs`; this account has 2/4 GiB, 4/8 GiB and 8/16 GiB), passed to the machine create (`Provider.AcquireSize`, `CreateRequest.VCPUs/MemMiB`). A label with no size gets the default size. A size that cannot be created (`raccoon-64vcpu`) is not left queued for ever: the service logs what the organization can create and cancels the run (`SizeError`). A waiting runner has only the labels `self-hosted` and the service's runner label (`raccoon-4vcpu`), and GitHub gives a job only to a runner with every label it names, so `consider` counts a waiting runner as able to take a job only when `waitingCanServe` (all the job's labels are those), and schedule and downstream anticipation skip jobs it would not serve: other sizes always get a machine of their own, with the cold start; keep-alive per size is not done. `serve -runner-label raccoon-2vcpu` makes the waiting runners that size (the machine size of a waiting runner follows its label), so one service keeps one size warm; that is how the 2-core comparison with GitHub-hosted runners was run. If reading the sizes fails, jobs of the default label still run (default size). Verified live: `raccoon-8vcpu` got `nproc` 8 and 16 GB; `raccoon-64vcpu` was refused with the message and the run cancelled, no machine created.
  - **Where a cold start goes** (measured 2026-10-31 from the runner's own log on the machine; `queued→started` 6–9 s against GitHub-hosted 2 s): machine create 1.6 s, the runner process starting 1–2 s, the runner authenticating and opening its session with GitHub about 2 s, GitHub handing it the job about 1 s, our own noticing under 0.5 s. A paused spare (`-warm`) no longer helps: resume takes 1.6–3.2 s against 1.6 s for a create, and the runner's own start-up is no faster on a warm machine, so `-warm` is off by default and should stay so. What is left is mostly GitHub's runner protocol; it can be hidden (an idle runner: 1–2 s) but not removed.
  - **Measured on InstaBox** (jobs queued→started as GitHub reports it): machine created for the job 10 s then, 6–9 s on 2026-10-31 when a create takes 1.6 s; paused spare (`-warm N`) 7–9 s; idle runner already online 1–2 s. GitHub-hosted runners were 3–4 s and InstaBox's own `instabox-medium` 12–20 s. Verified live: a chain `a → b → c` on `bench-lint-docs` (second run: b and c 2 s, the runners having been started 8 s before they were due); a job of `bench-go-integration` started in 2 s on a runner kept after a job of `bench-lint-docs` (organization pool). The keep-alive policy, the downstream prestart and the release of a taken job's runner have unit tests (fake GitHub and InstaBox); the live runs used a small number of runs, so the policy has not been evaluated on a real workload.
  - **Webhooks** (`webhook.go`, `cmd/raccoonci/webhooks.go`; `serve -webhook-listen ADDR -webhook-url https://…`): the user publishes ADDR (the sandbox's `instabox-port publish` needs the user's permission), `serve` makes a random signing secret (memory only, never printed), creates or updates one repository webhook per watched repository for `workflow_job`, `push` and `pull_request` events (needs `admin:repo_hook`; an existing hook with our URL is updated, others are not touched) and deletes them when it stops. `Webhook` rejects anything whose `X-Hub-Signature-256` (HMAC-SHA256 of the body, constant-time compare) is wrong before reading it; a delivery for a repository not watched, or before/after `Run`, gets 202 and the listing finds the job anyway. A `queued` job goes straight to `Service.consider` (the same decision a scan makes, so a redelivery or the scan finding it too starts nothing twice); `in_progress` and `completed` clear the promise a waiting runner made for the job and wake the loop to scan (durations, downstream jobs). With webhooks the repositories are listed only every `-safety-poll` (30 s); runners to start ahead or to let go are still checked every second, which costs no request. `consider` also fixed that a job whose launch failed was never retried. Unit-tested with fake GitHub and InstaBox (signature, a queued job started with the listing set to an hour, redelivery, foreign repository, hook registration and removal); verified live (2026-10-31, `bench-lint-docs` chain `a → b → c` pushed twice through a published port): GitHub's ping got 204, an unsigned POST through the public URL got 401, the job's runner was started 1.4 s after the delivery (machine 1.1 s), a cold first job started 7 s after being queued and the others 1–2 s, and the hooks, runners and machines were all gone after `serve` stopped.
  - **Events that are about to start workflows** (`event.go`): the webhook also takes `push` and `pull_request` (the hook is made for `workflow_job`, `push` and `pull_request`). On one, `anticipate` lists the repository's workflows, reads each at the event's commit, asks `trigger.Match` whether the event triggers it (branches, tags, `paths` from `ChangedFiles` through the compare API, or unknown when that cannot be had, activity types), counts the first jobs that need nothing, carry our label and which a waiting runner can serve (`instancesOf`, so a matrix counts as its jobs), and makes an expectation for that many runners, starting them at once and keeping them a minute. Measured live (2026-11-01, six pushes to a workflow on `bench-lint-docs`): GitHub queued the first job 2–3 s after the event reached us (every time), and with a runner started ahead that job began 5–7 s after being queued, against 6–9 s for a cold start: **about 1–2 s gained**, six runs, within the noise, one runner of the six unused. A runner needs about 7 s from its start to taking a job and GitHub gives only 2–3 s of that head start. The log says `the first job of the run for … was queued N s after the event reached us`. A pull request is read at its head commit, because `refs/pull/N/merge` does not exist yet when the event arrives (404 right after opening; `refs/pull/N/head` can be read).
  - **Which workflow file a run uses** (`workflowOfRun`): for most events the file at the run's `head_sha`; for `pull_request` (its merge commit), `pull_request_target` (the base branch) and `workflow_run` (the default branch) the ref after the `@` in the run's `path`, with the commit as a fallback if that cannot be read. `workflowFile` keeps what it read for good only when the ref is a full commit id, else for 5 minutes (it used to keep a branch for ever, so a changed cron on `main` was never seen). The path-ref reading is tested with a fake GitHub, not yet seen on a real pull request run.
  - **Not done / not verified:** organization-level webhooks (`admin:org_hook`; the repository hooks are one per watched repository); whether InstaBox's auto-suspend (30 min) treats a machine with a listening runner as idle; a real `schedule:` fire (cron is unit-tested only); `actions/cache` and artifacts go to GitHub's services on this path, redirecting them to `internal/cache` is untried; a `pull_request` event on real GitHub (only `push` was run live); the `if:` of a job is not evaluated when counting runners to start ahead (a job that will be skipped still gets one); keep-alive and pooling per machine size; the number of machine starts a minute (10 on InstaBox's Pro plan) is what limits a big fan-out, and the user is looking into raising it. The benchmark's prices file now has GitHub's current price ($0.006 a minute for 2 cores, read on 2026-10-31) and `instabox-medium` taken as the 4 vCPU / 8 GiB template (an assumption); GitHub-hosted is the 2-core runner (a 4-core one needs a paid plan), ours and InstaBox's are 4-core.
- `internal/semver`: npm-style version ranges as `setup-*` actions read them (`20`, `20.x`, `>=18`, `^1.22`, `1.2 - 1.4`, `||`). Pre-releases never match a range.
- `internal/runner`: runs one job instance the way GitHub's runner does.
  - `run:` steps use GitHub's exact shell command lines. Unspecified shell is `bash -e`, explicit `bash` adds `--noprofile --norc -o pipefail`, and `python` falls back to `python3` on Debian.
  - Step conditions use the job's status. Composite actions have their own steps, inputs and `success()`.
  - Supports `continue-on-error` (outcome vs conclusion) and step and job timeouts. Cancellation sends SIGINT, then SIGKILL to the step's process group. `always()` and post steps get a 5-minute grace period.
  - Workflow commands are supported in both `::x::` and legacy `##[x]` forms, and so are the file commands (`$GITHUB_ENV`/`OUTPUT`/`PATH`/`STATE`/`STEP_SUMMARY`).
  - Secrets and `add-mask` values are masked in every event.
  - JavaScript actions support pre, main and post, `INPUT_*`/`STATE_*`, and post-if defaulting to `always()`. Composite actions are supported too.
  - `set-env`/`add-path` are disabled unless `ACTIONS_ALLOW_UNSECURE_COMMANDS` is set, and `NODE_OPTIONS` is refused via `$GITHUB_ENV`, both as on GitHub.
  - A step ends when its shell exits, even if background processes keep the pipes open (`server &` works). Leftover processes are killed at job end.
  - Container jobs (`container:`) and service containers (`services:`) run through the docker command line (`internal/docker`; `containers.go`). Steps run with `docker exec` in a long-lived container made from the job's image (entrypoint `tail -f /dev/null`); every service gets a container on a network made for the job. The job's directories, the tool cache, the downloaded actions and the Node.js runtimes are bind mounted at the same paths as on the host (`Config.Mounts`, read-only), so file commands, working directories and action paths need no translation, and the host's docker socket is mounted too, as on GitHub's runners. A container job starts from its image's environment, not the host's; `run:` shells and `python` are looked up inside the container. A service is reached by its id from a container job, and through ports published on 127.0.0.1 (`job.services.<id>.ports`) from a host job; `ports:` without an address bind to loopback, unlike GitHub. The service is waited for until its health check says healthy (5 minutes). Secret values reach containers through the docker process's environment (`-e NAME`), never the command line; the few names the docker CLI reads itself go in a private env file. `docker exec` forwards no signals, so a step in a container is started through `/bin/sh -c 'echo $$ >pidfile; exec "$@"'`, with the pidfile in the job's temp dir (both sides see it). docker makes every exec its own process group leader, so that pid is the pgid; cancelling sends SIGINT, then SIGKILL after the grace period, to that group with another `docker exec … kill -- -pid` as root, and the docker client leaves when the process does. Images without `/bin/sh` fall back to signalling the docker client only; whatever is left goes when the container is removed at job end, together with the services and the network. A service without a health check must stay up for `settleTime` (1 s) before it counts as ready, so one that dies on start fails the job instead of being reported as running. After the job, files that root in the container left in the mounts are chowned back, unless docker is rootless. The artifact and cache services listen on 127.0.0.1, which is not the host from inside a container, so once the job's network exists the runner calls `Config.ContainerServices` with the network's gateway (the host's own address on it) and subnet. `raccoonci run` then serves the same handler on that one address, accepts only peers from that subnet (`local.OnlyFrom`), and gives container steps a `ServiceEnv` pointing there. Never widen this to all interfaces; the token and signed URLs are unchanged. Each listener's `http.Server.BaseContext` records its address (`blob.WithBaseURL`), and the upload and download links the services hand out are built on the address the request came in on, so an artifact uploaded from a container downloads on the host and back. Failure is a warning, not an error (rootless docker, whose networks are not on the host, is refused up front; a host firewall dropping INPUT is not detected). Verified with the real `upload-artifact@v4`, `download-artifact@v4` and `actions/cache@v4` (v1 and v2) in a `debian:trixie-slim` job container, with another docker network and the host's external address refused. A musl image (Alpine; detected by `/lib/ld-musl-*`) gets the musl Node.js (`Config.NodeMusl`, `nodejs.NewMusl`: builds from `unofficial-builds.nodejs.org`, the same host GitHub's runner uses, verified against its SHASUMS256.txt, kept in `node/musl/` so the existing mount covers it). That build links libstdc++ dynamically and Alpine lacks it, so when `node --version` fails there the runner runs `apk add libstdc++` as root in the job's container, with a notice in the step log; if that fails the error says to add it to the image. `TestRealAlpineNodeAction` takes `RACCOONCI_TEST_ALPINE_IMAGE` for a sandbox whose TLS proxy breaks apk's https mirrors. Credentials (`credentials:`) log in with a private `DOCKER_CONFIG` for the pull only, tested against a local `registry:2` with basic auth (`TestRealPrivateRegistry`). Not done: `--user` handling for images that do not run as root, and a sweep of containers orphaned by a killed process (they carry the label `raccoonci=1`). `TestRealContainerJob` and the other `TestReal*` tests in `internal/runner` need `RACCOONCI_TEST_DOCKER=1`.
  - Docker actions (`docker_action.go`): `uses: docker://image` and `runs.using: docker` run with `docker run --rm` on the host's docker (even in a container job), the way GitHub's runner does: the workspace, temp, tool cache, file commands, event directory and a home are mounted at `/github/...` and `/opt/hostedtoolcache`, the path-valued `GITHUB_*`/`RUNNER_*` variables are rewritten to those, this machine's own environment and PATH are not passed (`envFor(..., host=false)`), the job's network is joined if there is one. `image: Dockerfile` is built from the action directory once per job. Output and cancellation go through `runCmd` (shared with `exec`): SIGINT is proxied by the docker client, and after the grace period `onKill` runs `docker kill`, since killing the client leaves the container. Afterwards the image's own `chown` gives root-written files back (best effort). `runs.args` is passed to pre and post entrypoints too (from memory of the runner, unconfirmed). Verified with `actions/hello-world-docker-action@v2`; `TestRealDockerActions` needs `RACCOONCI_TEST_DOCKER=1`.
  - Not yet supported: problem matchers.
- `internal/engine`: runs the job graph.
  - Jobs wait for their `needs`. Job `if:` uses `expr.Status`, where `Skipped` means a need didn't succeed. `failure()` is transitive over ancestors.
  - Matrices are expanded at run time, so `fromJSON(needs...)` works.
  - Supports fail-fast, `max-parallel`, and job-level `continue-on-error`.
  - Unavailable OSes fail that instance with `platform.Unavailable`, per the product rule, before it waits for a `max-parallel` slot.
  - Reusable workflows are not supported yet.
- `internal/actions`: parses `action.yml`. Unknown keys are ignored, as GitHub does. It also downloads actions: through codeload without a token, through the API with one, and once per `Store`, because tags move.
- `internal/archive`: tar.gz extraction through `os.Root`. Entries can't escape the destination via `..`, absolute paths, symlinks or hard links.
- `internal/nodejs`: knows nodejs.org: the release index (`Index`) and verified downloads (`Fetch`). `Runtime` builds on them to provide the Node.js that JavaScript actions run on, and uses an installed version when offline; `provision` uses them to install the Node.js a job asks for. `NewMusl`/`FetchMusl` do the same for the musl builds on `UnofficialBaseURL` (not every release has one: the index's `files` list decides which version is "newest").
- `internal/local`: support code for `raccoonci run`.
  - Builds the github context from git.
  - Implements checkout by copying the working tree.
  - Renders the terminal output.
- Deliberately not depending on act's `pkg/model` (it pulls in go-git/logrus and silently drops dynamic matrices), on actionlint's AST (it stringifies all scalars, so `false` would become truthy), or on actionlint at all (12 direct deps for a ~500-line parser). act and actionlint are fine as reference implementations.
